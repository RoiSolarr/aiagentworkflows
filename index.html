How it works

Six steps, and a human gate at step five

The agent runs the moment the form is submitted. It finishes its thinking in seconds, writes everything to Airtable, and then the workflow deliberately stops and asks a person.

  1. 01

    Form

    A visitor submits the Jotform embed. CAPTCHA and Turnstile filter the obvious bots.

  2. 02

    Make

    A webhook checks a secret token, parses the payload and validates the fields before spending anything.

  3. 03

    AI agent

    It scores, classifies, researches the URL with Firecrawl if there is one, and picks a recommended action.

  4. 04

    Airtable

    Score, category, reasoning and the draft reply land on the record. Status becomes Pending Approval.

  5. 05

    Slack approval

    A human reads the draft and clicks Approve or Reject. Until then nothing is sent. This is the gate.

  6. 06

    Reply

    A second scenario checks the single use token, sends the Gmail reply and closes the record.

Why the gate exists. An agent that can send email on its own is one bad classification away from embarrassing you in front of a real customer. Keeping a person on the send button costs about four seconds per lead and removes that entire class of failure.

Use cases

One agent, three modes

The inquiry type you pick on the form decides which mode the agent runs in. Same agent, same JSON schema out, different job.

Sales inquiry

Lead qualification

Scores the lead from 0 to 100 on fit, intent, budget signals, urgency and whether the company looks real. Hot at 75 and above, warm from 40, cold below that, or flagged as spam.

  • Book a call
  • Send a tailored reply
  • Request more info
  • Escalate to a human
  • Discard

Support request

Support triage

Classifies the category as billing, technical, account or other, sets a priority, and drafts a reply in the right register. Anything urgent, angry or legal is escalated rather than answered.

  • Category and priority
  • Drafted response
  • Automatic escalation

Research request

Research assistant

Scrapes the supplied URL with Firecrawl once, then writes a five bullet brief and a draft email grounded in what it actually read. If the scrape fails it says so instead of inventing a company.

  • One scrape per submission
  • Five bullet brief
  • No invented facts

What happens after you submit

  1. ~1s Make validates the token and your fields.
  2. ~3s The agent scores and drafts. Firecrawl runs only if you gave a URL.
  3. ~4s Airtable record set to Pending Approval.
  4. ~5s A Slack message lands with the draft and two links.
  5. then Nothing, until a human clicks.

Submissions are stored in a private Airtable base for this demo and are not used for anything else. Put in fake details if you would rather not share real ones. The agent treats everything you type as untrusted data, so prompt injection attempts are welcome and will be ignored.

Three things worth knowing

The credit model drove the architecture
Agent runs are billed per operation plus tokens, so the tool call cap and the single scrape rule are budget decisions, not style ones.
Parsing Jotform is the fiddly part
The payload arrives form encoded with the real data hidden in a rawRequest JSON string, and the name field is an object rather than a string.
Approval tokens have to be single use
Without that check, a forwarded Slack message is a re-send button that anyone can press twice.

FAQ

Reasonable questions

Is the agent actually deciding, or is this a decision tree in disguise?

It decides. The agent is given the form content, a set of tools and a description of the five actions it can recommend, and it chooses one along with a score, a category and a draft. The router in Make only carries out whatever the agent returned. What is fixed is the schema it has to answer in, not the answer.

What stops someone pasting instructions into the message field?

The system prompt tells the agent to treat everything from the form as untrusted data and to ignore instructions found inside it. That handles the common cases. It is a mitigation rather than a guarantee, which is exactly why the human approval gate exists: a successful injection still has to get a person to click Approve on an obviously wrong draft.

How is the approval link secured?

Each submission gets a random token stored on its Airtable record. The approval page passes it back to a second Make scenario, which checks that the token matches that record and has not been used before, then marks it used. A second click on the same link does nothing. The page itself shows only the action being confirmed, never the lead's details.

Does the Turnstile check really protect the form?

Partly, and it is worth being straight about this. Turnstile sits on this page and is verified server side before the form is revealed, which stops casual bots. The form itself is a Jotform iframe with its own URL, so a determined bot can post to Jotform directly and skip this page. Jotform's own CAPTCHA and the secret token check in Make are what cover that gap. A custom form posting through the verification function would close it properly.

What happens if Firecrawl or the agent fails?

Error handler routes catch it. The record is set to Status = Error with the failure written to an Error Log field, and a Slack alert goes out. If the agent returns something that is not valid JSON, the record goes to Needs human review instead. Nothing fails silently and nothing half sends.
